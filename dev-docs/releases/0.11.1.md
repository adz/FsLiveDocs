## FsLiveDocs 0.11.1

### Fixed

- `init` now fills `siteName` from a single root solution name, falling back to the repository folder, while preserving other config values.
- The starter `docs/index.md` now uses `dotnet livedocs` for its command examples, matching local tool installation.
- The getting-started guide now puts the six setup steps first: enable XML documentation, build projects, choose the home page and site name, follow the link rules, and account for numbered filenames.
- `init` now asks whether an existing `docs/README.md` should be the home page when `docs/index.md` is absent. Builds warn while the generated starter index remains unedited.
- Audits now show every compiler error in each F# block with line and column coordinates.
- Builds warn when a configured project has no adjacent XML documentation file, which means it has no API pages; `--warn-as-error` promotes that warning. `init --discover-projects` also checks the effective setting and prints the line to add.
- Builds now invalidate cached sites when configured project inputs, assemblies, or XML documentation change. The watcher also rebuilds when those compiled outputs change.
- Builds now collect every broken local page link across API and guide pages before failing, so the full set can be fixed in one run.
- Broken page-link errors now show the resolved source and output paths, identify folder targets and pages whose generated names differ, and explain how to handle links outside the docs root.
- Local Markdown links now resolve from their source paths before page slugs are applied, so case changes and number-prefixed filenames resolve to the right page. A link to a stripped name that does not exist no longer passes by matching the generated slug.
- Builds now select line-oriented progress automatically when standard output is redirected, avoiding Spectre's live display on scripts and redirected Windows consoles.
- Transcripts and `run` blocks no longer type-check against the tool's own Axial. The worker process shipped beside FsLiveDocs.Runner, whose folder also holds the Axial assemblies FsLiveDocs is built on, and the F# compiler inside it resolves an assembly's dependencies from that folder. On a page whose project was an Axial package such as `Axial.HttpClient`, the package was referenced before its `Axial.dll`, so examples bound to the tool's Axial 0.9.1 and failed with `FS0039` or `FS1093` wherever they used a newer API. The worker now runs from a copy that holds only itself, FSharp.Core, and FSharp.Compiler.Service, staged once per process under the temporary directory.
- `run` blocks, transcripts, and snapshot examples run against the same build the audit compiles: the project's sole or first target framework, in the default configuration when built and in Release otherwise. They used the most recently written assembly under `bin` or `artifacts/bin`, so a multi-targeting build could hand an example `net8.0` for one package and `netstandard2.1` for its dependency, failing with errors such as "The module/namespace 'System.Threading' from compilation unit 'System.Runtime' did not contain the namespace, module or type 'CancellationToken'".
