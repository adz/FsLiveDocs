## FsLiveDocs 0.3.2

Fix duplicate entity/example extraction for doubly-nested modules and types.

### Fixes

- `SymbolLister.extractFromProjectWithDiagnostics` counted every doubly-nested module, or nested
  type case, twice: once via its parent's own recursive mapping, and again because
  `ApiDocModel.EntityInfos` ("the full list of all entities", per FSharp.Formatting's own doc
  comment) already lists every nested entity as its own root-level entry in addition to nesting
  it under its parent. The old code additionally recursed into `NestedEntities` on top of that
  already-flat list, so a pattern such as `module M = module Advanced = let f = ...` produced two
  copies of `Advanced` and everything under it.
- Consumer-visible symptom, reproduced by a real adopter (Reified) migrating its docs:
  `audit`/`build`/`test` raised `Duplicate documentation block id: <Owner>#example-<Name>` for
  any XML `<example>` on a member of a doubly-nested module, because the uncovered-example walk
  (`GeneratedVerification.compileUncoveredExamples`) visited the same example twice. This also
  inflated the "N unnamed parameter" / "N examples do not compile" `audit` counts for any assembly
  with this nesting shape, since `parameterDiagnostics` walked the same duplicated list.
- Fixed in `SymbolLister.extractFromProjectWithDiagnostics`: filter `EntityInfos` down to entities
  with no `ParentModule` (genuine roots) before mapping, and let each root's own recursive
  `mapEntity`/`parameterDiagnostics` supply its descendants exactly once. `Packages.EntityIds`
  (used to attribute a nested type or module to its owning package) now walks the resulting,
  correctly-nested tree directly instead of reading the old flat-with-duplicates list.
- No known effect on flat (non-nested) modules or on the merged multi-project model — `merge`'s
  `reconstructHierarchy` already expects genuinely flat, non-duplicated per-package entities and
  is unaffected by no longer receiving pre-duplicated ones.

### Known issue, not fixed by this release

`capture` can still raise `Release API artifact contains duplicate member ID <Id>` for a type and
its same-named companion module (F#'s `type X = ...` / `module X = ...` pairing, e.g. Reified's
`Interval<'value>` type alongside `module Interval`). Root-caused as far as: a single extraction
pass of the owning project alone is clean (the member appears once in `mapEntity`'s output, and
once more after `SymbolLister.merge`'s `reconstructHierarchy`/`pruneSyntheticDefaults`), yet
`ReleaseCapsule.validateApi` — called immediately afterward on that same in-memory
`ApiModelArtifact`, no serialization round-trip in between — still reports a duplicate. Not
reproduced by `audit` or `build`, only by `capture`. Needs a fresh investigation pass, ideally by
someone who can step through `ReleaseCapsule.create`/`validateApi` directly with a debugger rather
than print-instrumentation, since instrumenting the merge output did not reveal where the second
copy comes from.
